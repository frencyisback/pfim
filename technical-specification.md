# Technical Specification — Personal Finance & Investment Manager (PFIM)

**Document/product specification version:** 1.0  
**Last revised:** September 12, 2026  
**Status:** living normative specification, application 0.22.0 + `[Unreleased]` changes  
**Type:** local, single-user web application, accessible only over loopback  
**Guiding principles:** Sound abstraction · Consistency · Efficiency · Effective documentation

> **Separate versions.** `1.0` (or `v1` for short) identifies the version of this
> product specification, not the software release or the version of the HTTP
> prefix `/api/v1`. The application version is independent and is declared by
> the backend OpenAPI, the frontend `package.json`, and `CHANGELOG.md` (latest
> release: 0.22.0). Changes implemented in the repository but not yet released
> are marked `[Unreleased]`.

### Requirement status

The following labels distinguish existing behavior from approved work that
has yet to be implemented:

- **[IMPLEMENTED]**: behavior present in the current repository revision, the
  reference release, or `[Unreleased]`;
- **[PLANNED]**: a normative requirement approved for a later development cycle;
- **[SUPERSEDED]**: a historical decision that no longer applies, retained only
  where it helps explain a transition;
- **[OPEN DECISION]**: an item that cannot be implemented until a policy has
  explicitly been selected;
- **[KNOWN DIVERGENCE — R-xx]**: a desired requirement not yet satisfied by the
  current code; the actual behavior and resolution plan are documented under
  the corresponding ID in `docs/risk-register.md`.

Without a label, the text describes normative **implemented** behavior. A
section marked `[PLANNED]` must not be presented to users as already available.

### Scope and sources of truth

This specification defines domain rules, invariants, and expected behavior.
To reduce duplication that has previously caused inconsistencies:

1. The **HTTP contract actually exposed** is the OpenAPI generated by FastAPI
   at `/docs`; this specification describes its semantics and identifies
   planned changes separately.
2. The **deployed schema** is the Alembic migration chain. SQLAlchemy models
   represent the current schema, and
   `backend/tests/integration/test_migrations_match_models.py` compares tables,
   columns/types/nullability, seed data, and declared index presence. Foreign
   keys, CHECK constraints, UNIQUE constraints, defaults, and `ondelete`
   policies are also protected by fail-closed migrations and dedicated domain
   tests, but that individual test does not yet compare them generically and
   exhaustively.
3. Formulas, edge cases, and financial conventions are defined here and
   detailed in `docs/finance-calculations.md` and `docs/multi-currency.md`; the
   pure code in `backend/app/finance/` is their verifiable implementation.
4. `README.md` and `docs/setup.md` are operational guides, while `CHANGELOG.md`
   is a history; they do not replace normative requirements.
5. `docs/risk-register.md` records verified but unresolved defects and
   proposals. It does not describe available behavior until the corresponding
   risk has been resolved in code, tests, and this specification.

If an `[IMPLEMENTED]` description differs from OpenAPI, models, or tests, that
is a documentation or application defect to resolve; it must not be covered
up by implicitly inventing behavior.

## 1. Vision and Objectives

### 1.1 Description

**PFIM** (Personal Finance & Investment Manager) is a local, single-user web
application for integrated tracking of cash flows, investment portfolios
(stocks, bonds, ETFs), and long-term wealth projections.

The frontend, API, and database run on the user's machine. Development and
production servers must listen exclusively on loopback interfaces
(`127.0.0.1`/`localhost`): the absence of authentication is acceptable only
within this boundary. PFIM core requires no cloud services.

### 1.2 Primary Objectives

| # | Objective | Priority |
|---|-----------|----------|
| O1 | Complete income and expense tracking with categorization | High |
| O2 | Securities portfolio management (purchases, sales, coupons, dividends) | High |
| O3 | Return calculations using multiple metrics (TWR, MWR/IRR, Total Return) | High |
| O4 | Security price updates through CSV imports | High |
| O5 | Concise financial reports and dashboards | High |
| O6 | Wealth forecasts over a 1–50 year horizon | Medium |
| O7 | Flexible fee and tax tracking | Medium |
| O8 | Multiple currency support (EUR, USD, GBP, CHF, others) | Medium |

### 1.3 Outside the Scope of Specification 1.0

- Authentication and multiple users
- Publishing on a LAN/the Internet or access from remote devices
- Synchronization with bank or online broker APIs
- Automated trading or push notification alerts
- Alternative asset management (real estate, cryptocurrencies, metals)

Any access beyond loopback requires a separate architectural decision,
authentication, transport protection, a CORS review, and a threat model; it is
not a simple startup option.

## 2. Technology Stack

### Rationale

The stack prioritizes reproducible local installation, limited dependencies,
and verifiable calculations using decimal arithmetic.

### 2.1 Backend

| Component | Technology | Reference version | Role |
|-----------|------------|-------------------|------|
| Runtime | **Python** | 3.14.6 | API, services, and calculations |
| API framework | **FastAPI** | constrained in `backend/requirements.txt` | REST and OpenAPI |
| ASGI server | **Uvicorn** | constrained in `backend/requirements.txt` | HTTP service on loopback |
| ORM | **SQLAlchemy** | 2.x | persistence and queries |
| Migrations | **Alembic** | 1.x | incremental schema versioning |
| Database | **SQLite** | Python runtime | local single-user storage |
| Validation/configuration | **Pydantic** + **pydantic-settings** | 2.x | contracts and settings |
| Financial calculations | pure modules in `backend/app/finance/` | internal code | `Decimal`, TWR, MWR/XIRR, and metrics |
| Dependency management | **pip** + `pylock.toml` | Windows AMD64/Python 3.14 lock | reproducible backend virtual environment |

`numpy`, `numpy-financial`, and `pandas` are not backend dependencies. MWR/XIRR
uses an internal documented and tested solver. Alembic versions migrations,
but does not itself guarantee a risk-free rollback: a verified backup is
required before upgrading or downgrading. Application restore is a separate,
opt-in maintenance procedure and is not an automatic rollback implied by
this precaution (§6.12).

SQLite is an architectural choice for the local profile. A possible move to
PostgreSQL would require at least a review of queries, types, concurrency,
migrations, configuration, and tests; changing the connection string alone
would not be sufficient.

`backend/requirements*.txt` declare direct dependencies; they are not by
themselves a reproducible lock. The reference Windows environment installs
`backend/pylock.toml`, which fixes versions, wheels, and hashes, with
`--require-hashes`. `backend/constraints-tested-win-py314.txt` also records
validated transitive versions. The POSIX path applies the same version
constraints but does not yet have platform-specific hashed locks: it is
therefore a best-effort path, not equivalent to the Windows guarantee (`R-13`).

`.node-version`, `packageManager`, and `engines` pin frontend runtimes;

### 2.3 Local Deployment

```text
[Browser localhost:5173] ←HTTP/JSON→ [FastAPI 127.0.0.1:8000] ←SQLAlchemy→ [Local SQLite]
```

During development, the frontend and backend are separate processes started
as described in `docs/setup.md`. Windows provides `start.bat` and the
PowerShell scripts in `scripts/`; the `Makefile` provides the POSIX targets
`dev-backend`/`dev-frontend`, while `make dev` only prints instructions for
starting them in two terminals. The database path comes from backend
configuration; without overrides, the code uses the isolated development
database `data/pfim-dev.db`. The supported profile uses a single backend
instance. This specification does not assume or authorize deleting or
replacing an operational database.

## 3. System Architecture

### 3.1 Layer Diagram

```text
┌─────────────────────────────────────────────────────────┐
│                     FRONTEND (React)                    │
│  Dashboard · Transactions · Portfolio · Reports · Forecast│
└────────────────────────┬────────────────────────────────┘
                         │ HTTP/JSON (REST)
┌────────────────────────▼────────────────────────────────┐
│                  API LAYER (FastAPI)                    │
│           Router · Schema Validation · OpenAPI          │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────┐
│               SERVICE LAYER (Business Logic)            │
│  TransactionService · PortfolioService · FinanceEngine  │
│  ForecastService · ImportService · ReportService        │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────┐
│             PERSISTENCE LAYER (SQLAlchemy)              │
│        Session · concrete repositories · ORM models    │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────┐
│                    DATABASE (SQLite)                   │
│             file configured by the environment         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 Separation of Responsibilities

- **Router (FastAPI):** HTTP parsing, validation, and delegation; it may
  translate domain errors into HTTP responses but contains no financial formulas.
- **Service layer:** orchestrates logic and transactions; the current
  implementation also receives the SQLAlchemy `Session` and uses repositories
  or ORM queries.
- **Persistence layer:** models and concrete repositories centralize reusable
  queries. `BaseRepository` is a generic SQLAlchemy helper, not an abstract
  interface or an in-memory backend.
- **Finance engine:** pure modules without database access or side effects,
  testable in isolation.

The frontend sends and receives JSON in `snake_case`, matching the Pydantic
schemas. There is no general conversion to `camelCase`.

### 3.3 Error Handling

Errors are classified as follows:

| Code | Type | Example |
|------|------|---------|
| 400 | Domain rule | Inconsistent transfer, unknown currency |
| 403 | Local HTTP boundary | Origin or capability not allowed |
| 404 | Resource not found | Unknown security |
| 409 | Logical conflict | Selling more shares than held |
| 413 | Payload limit | CSV exceeds the configured maximum |
| 422 | Schema/import validation | Required field or invalid CSV |
| 503 | Operational resource unavailable | SQLite busy or restore disabled |
| 500 | Internal error | Unhandled exception |

Structured domain errors may use this schema:
```json
{
  "error_code": "INSUFFICIENT_SHARES",
  "message": "Attempted to sell 150 shares; 100 available",
  "detail": { "ticker": "ENI.MI", "requested": 150, "available": 100 }
}
```

`PFIMError` domain errors and FastAPI/Pydantic validation errors are translated
into the same envelope. Validation uses the code `VALIDATION_ERROR`, and
`detail.fields` contains per-field messages; the frontend must still provide
a fallback for HTTP errors not produced by these handlers, such as
infrastructure failures.

### 3.4 SQLite Transactions and Concurrency

A request uses a single unit of work: repositories and services run `flush`,
while the commit occurs exclusively at the FastAPI boundary. Any exception
rolls back the entire composite flow. Reads explicitly open `BEGIN`, and
mutations use `BEGIN IMMEDIATE`, so check-then-write checks for FIFO,
categories, deduplication, and sale costs serialize writers even across
separate connections.

Every connection enables foreign keys and `busy_timeout`. `SQLITE_BUSY` and
`SQLITE_LOCKED` become structured 503 errors, and non-idempotent mutations are
not retried automatically. SQLite remains a single-writer database:
correctness and rollback do not imply unlimited concurrent throughput, and
the supported profile uses one backend instance (`R-04`).

## 4. Data Model

### 4.1 Entity Relationships (Narrative Description)

The model covers six areas: **cash flow and categories**, **portfolio and
income**, **prices and exchange rates**, **taxes and costs**, **forecasts**,
and **import configuration**.

### 4.2 Main Tables

**[IMPLEMENTED — Unreleased] Application numeric policy.** SQLite treats
`NUMERIC(p,s)` as affinity and does not enforce its precision and scale during
binding. All application writers therefore canonicalize decimals using
`ROUND_HALF_EVEN` **before** using them in derived calculations and before
persistence. The canonical representation and accepted domain are:

| Logical type | Canonical scale | Application domain |
|--------------|-----------------|--------------------|
| amounts, quantities, and prices `NUMERIC(18,6)` | 6 decimal places | absolute value ≤ 999,999,999 |
| exchange rates `NUMERIC(18,8)` | 8 decimal places | 0.00000001 to 9,999,999, strictly positive |
| percentages/rates `NUMERIC(8,4)` | 4 decimal places | absolute value ≤ 9,999; any domain constraints apply in addition to this technical limit |

These limits deliberately remain below the nominal DDL capacity, providing a
verified margin for preserving the final declared digit during round trips
on the reference SQLite runtime. The DDL remains broader for historical
compatibility, but does not alone define the write contract. A nonzero input
that would become zero at the required scale is rejected; explicit zero
remains valid only in fields that permit it. Derived results may instead
become zero when no persistable quantity exists: for example, an automatic
capital gain/loss that canonicalizes to zero at six decimal places does not
create a tax event. Sign rules and tax rounding to cents remain separate
constraints.

#### `categories` — Income/Expense Categories
```sql
id              INTEGER PRIMARY KEY
name            TEXT NOT NULL UNIQUE        -- e.g. "Salary", "Rent", "Groceries"
type            TEXT NOT NULL               -- 'income' | 'expense' | 'transfer'
parent_id       INTEGER REFERENCES categories(id)  -- hierarchy (e.g. Food > Groceries)
color           TEXT                        -- hex color for the UI
icon            TEXT                        -- icon name
is_system       BOOLEAN NOT NULL DEFAULT FALSE -- system-provided category; deletable when unused
```

A fresh installation has no preseeded categories. Users create their own
categories; the dedicated transfer, trade, income, and cost workflows create
their required automatic categories on demand as described in §5.2 and §5.6.

**[IMPLEMENTED — Unreleased] Name identity.** Creation and resolution by name
use the key `name.strip().casefold()`: surrounding whitespace and Unicode
letter case are ignored, while accents and internal spaces are preserved.
New names must be globally unique, including across different types and
parents; a collision returns 409. Lookups distinguish no matches, one match,
and multiple matches: an ambiguous name returns the IDs involved, without
selecting the first category or inferring it from the amount's sign. The map
is built once per operation/import and is not retained in a global cache.

Legacy categories with matching names remain readable and usable through an
explicit ID, subject to the other domain rules. They are not merged, renamed,
or reassigned. During imports, ambiguity is a row error; in composite
operations it causes a conflict with a full rollback. Automatic category
resolution also requires the correct type and no children before writing
within the serialized transaction.

**[IMPLEMENTED — Unreleased] Leaf rule.** A category can be assigned to a
transaction if and only if it has no children. A root without children is
therefore a valid leaf; a root with subcategories is only a grouping node.
The rule applies to manual entry, CSV imports, and system-generated movements.

Creating the first child under a category already used by transactions is
prohibited with `409`: it would retroactively turn that category into an
unassignable grouping node. The restriction remains while the category is
referenced. Manual movements must be deleted and, if appropriate, recreated
with a leaf; generated movements must be handled through their source entity.
The system does not move data or automatically choose another category.

#### `accounts` — User Checking/Deposit Accounts
```sql
id              INTEGER PRIMARY KEY
name            TEXT NOT NULL               -- e.g. "Checking Account", "Savings Account"
type            TEXT NOT NULL               -- 'checking' | 'savings' | 'investment' | 'cash'
currency        TEXT NOT NULL DEFAULT 'EUR'
opening_balance DECIMAL(18,6) NOT NULL DEFAULT 0
is_active       BOOLEAN NOT NULL DEFAULT TRUE
opened_on       DATE                        -- inclusive opening date; NULL only for unknown legacy dates
closed_on       DATE                        -- inclusive closing date; NULL = no known closing date
notes           TEXT
reference_account_id  INTEGER REFERENCES accounts(id)  -- required when type='investment' (§5.2)
```

`opening_balance` is canonicalized to six decimal places and checked against
the application domain in §4.2 on both creation and update, before account-type
accounting checks. A nonzero amount that would become zero, or a value beyond
the limit, is rejected with a structured error rather than leaving the
decision to the SQLite round trip.

**[IMPLEMENTED — Unreleased] Temporal lifecycle.** For new accounts,
`opened_on` is the user-provided date or today's date when omitted; future
dates are prohibited. Boundaries are inclusive and `closed_on >= opened_on`.
The columns remain nullable because legacy records have no reliable source
from which dates could be inferred: `NULL` means an unknown boundary and
makes the account present in the corresponding temporal direction.

Version 1 deliberately represents a single interval `[opened_on, closed_on]`.
An account deactivated today may be reactivated on the same day; a historical
closure cannot be removed by reactivation, which would make the account
reappear retroactively. A new interval requires a new account record. An
inactive account retains its entire history as read-only and accepts neither
new writes nor deletion of movements or financial sources.

Deactivation requires a zero current balance, no dependent active investment
account, no open position, and no future transaction, trade, coupon/dividend,
or recurring cost. Type and opening balance define accounting identity: they
cannot be edited once the account has entered the history. Permanent deletion
is allowed only for an account with a zero opening balance and no
transactions, trades, income, costs, or dependent accounts; no cascading
deletion removes financial data.

Usage checks include both `account_id` and `cash_account_id` on Trade,
IncomeEvent, and PortfolioCost, counting each source only once. The historical
cash account remains a dependency after an investment account changes its
reference account, including for zero-net income with no generated
transaction. These dependencies block permanent deletion and incompatible
accounting identity changes with 409 and counts. Deactivation instead
distinguishes future sources from completed history: a past reference alone
does not prevent archiving when the other requirements are met. No source
is moved or reconstructed.

#### `transactions` — Income and Expenses
```sql
id              INTEGER PRIMARY KEY
account_id      INTEGER NOT NULL REFERENCES accounts(id)
category_id     INTEGER NOT NULL REFERENCES categories(id)
date            DATE NOT NULL
amount          DECIMAL(18,6) NOT NULL CHECK (amount <> 0)
                                             -- positive = income, negative = expense
currency        TEXT NOT NULL DEFAULT 'EUR'
amount_eur      DECIMAL(18,6) NOT NULL      -- normalized to EUR at the day's exchange rate
fx_rate         DECIMAL(18,8) NOT NULL DEFAULT 1 -- applied exchange rate
description     TEXT
notes           TEXT
import_source   TEXT                        -- CSV import reference (idempotency)
import_hash     TEXT UNIQUE                 -- CSV row hash for deduplication (includes account, §8.1)
tags            TEXT                        -- JSON array of free-form tags
transfer_group_id  TEXT                     -- ID shared by the two transactions in a transfer (§6.1)
trade_id        INTEGER REFERENCES trades(id)         -- generated by a purchase/sale (§5.2)
income_event_id INTEGER REFERENCES income_events(id)  -- generated by a coupon/dividend (§5.2)
portfolio_cost_id INTEGER REFERENCES portfolio_costs(id) -- generated by a recurring cost (§5.6)
created_at      DATETIME DEFAULT NOW()
updated_at      DATETIME
```

**[IMPLEMENTED — Unreleased] Cash movement invariants.** Every persisted
transaction must have `amount != 0` and a mandatory `category_id` referencing
an existing category assignable under the leaf rule. Shared application
validation protects manual entry, CSV preview and confirmation, and internal
generators; the `CHECK` and `NOT NULL` constraints also protect the schema.
A valid income event with zero net income remains recordable but does not
generate a zero-value cash transaction.

An `income` category requires a strictly positive amount; an `expense`
category requires a strictly negative amount. A `transfer` category is
rejected by ordinary entry and CSV imports: it may only be used by the
dedicated workflow that atomically creates the two movements linked through
`transfer_group_id`.

Migration `a9e5c7d2b4f1` makes `transactions.category_id` non-nullable and adds
`CHECK (amount <> 0)`. Before rebuilding the SQLite table, it also checks for
missing or non-leaf categories, inconsistencies between sign and type, and
transfers missing the dedicated link. If incompatibilities are found, it
stops with counts, without backfilling or automatic corrections.

#### `securities` — Security Master Data
```sql
id              INTEGER PRIMARY KEY
ticker          TEXT NOT NULL UNIQUE        -- e.g. "ENI.MI", "AAPL", "BTP-2028"
name            TEXT NOT NULL
type            TEXT NOT NULL               -- 'stock' | 'bond' | 'etf_equity' | 'etf_bond' | 'fund' | 'commodity'
                                            -- legacy 'etf': readable, no longer offered in the UI
market          TEXT                        -- 'MIL' | 'NYSE' | 'NASDAQ' | 'LON' | ...
currency        TEXT NOT NULL               -- quotation currency
isin            TEXT UNIQUE
sector          TEXT
industry        TEXT
country         TEXT
coupon_rate     DECIMAL(8,4)               -- bonds only: coupon rate %
coupon_freq     TEXT                        -- 'monthly'|'quarterly'|'semiannual'|'annual'
maturity_date   DATE                        -- bonds only
face_value      DECIMAL(18,6)              -- face value
notes           TEXT
is_active       BOOLEAN NOT NULL DEFAULT TRUE
```

`sector`, `industry`, and `country` are optional scalar, free-text
classifications of the entire security (application limits of 100, 120, and
60 characters respectively). They provide a concise view of the current
portfolio; they do not model external taxonomies or weighted exposure to
individual ETF holdings. An ETF can therefore have just one user-selected
label per field and must not be presented as an accurate comparison of its
underlying markets or selection methods. Reversible migration `c3f8a1d6e4b2`
adds `industry` while preserving existing fields and rows.
Bond numeric metadata remains optional and flexible, but when provided it is
canonicalized before persistence: `coupon_rate` to four decimal places and
`face_value` to six, within the respective application limits in §4.2.
Normalization applies on both creation and update and does not make any
nullable model field mandatory.

Creation and updates share metadata constraints. The name must contain 1–200
characters and cannot be empty or consist solely of whitespace;
`coupon_freq` permits `monthly`, `quarterly`, `semiannual`, and `annual`.
During updates, an omitted field remains unchanged; `null` clears only
optional metadata. `name=null`, `is_active=null`, and unsupported frequencies
return 422 before writing. Reads preserve supported legacy data, including
the `etf` type, without implicitly normalizing it.

Deactivating a security requires zero quantity **in every investment account
as of today**, including today's trades, and no running deficit in its
history. Future trades and income with future payment dates are a separate
blocker, even when future trades offset one another or the income has a zero
net amount. A 409 conflict exposes investment accounts, sources, dates, and
reasons. Future quotes and maturity metadata alone do not prevent
deactivation. Reactivation follows the ordinary path; history is not corrected.

#### `trades` — Security Purchases and Sales
```sql
id              INTEGER PRIMARY KEY
security_id     INTEGER NOT NULL REFERENCES securities(id)
account_id      INTEGER NOT NULL REFERENCES accounts(id)
cash_account_id INTEGER REFERENCES accounts(id) -- frozen historical cash account; NULL only for unreconstructable legacy records
type            TEXT NOT NULL               -- 'buy' | 'sell'
date            DATE NOT NULL
quantity        DECIMAL(18,6) NOT NULL
price           DECIMAL(18,6) NOT NULL      -- unit price in the settlement currency
quote_price     DECIMAL(18,6) NOT NULL      -- unit price in the security's quotation currency
currency        TEXT NOT NULL               -- may differ from the security's quotation currency
price_eur       DECIMAL(18,6) NOT NULL     -- price in EUR at the day's exchange rate
fx_rate         DECIMAL(18,8) NOT NULL DEFAULT 1
total_amount    DECIMAL(18,6) NOT NULL     -- quantity × price (in the settlement currency)
total_eur       DECIMAL(18,6) NOT NULL     -- total in EUR
notes           TEXT
created_at      DATETIME DEFAULT NOW()
updated_at      DATETIME
```

`price` and `quote_price` are not synonyms. The former determines the cash
outflow/inflow in the settlement currency and therefore
`price_eur`/`total_eur`; the latter feeds native-currency FIFO and price
history in `securities.currency`. If the currencies match, an omitted
`quote_price` is canonicalized to `price`, and a different value is rejected.
If they differ, `quote_price` is required. For a security quoted in EUR, it
must also match `price_eur` at `NUMERIC(18,6)` precision.

Quantities, prices, and derived values (`price_eur`, `total_amount`,
`total_eur`) are canonicalized to six decimal places; the applied or implied
exchange rate is canonicalized to eight. They must fit the application
domains in §4.2 without turning nonzero input into zero. These checks occur
before persistence regardless of whether a price already exists for the
security/date. In EUR FIFO, the frozen `total_eur`, also authoritative for
cash, is allocated to the lot as `total_eur / quantity`: multiplying only the
six-decimal unit `price_eur` by quantity again would amplify rounding for
large quantities.

#### `trade_costs` — Fees and Charges per Trade
```sql
id              INTEGER PRIMARY KEY
trade_id        INTEGER NOT NULL REFERENCES trades(id)
cost_type       TEXT NOT NULL               -- free-form string; the UI suggests commission | tax | spread | other
description     TEXT
amount          DECIMAL(18,6) NOT NULL
currency        TEXT NOT NULL DEFAULT 'EUR'
fx_rate         DECIMAL(18,8) NOT NULL DEFAULT 1
amount_eur      DECIMAL(18,6) NOT NULL
percentage_used DECIMAL(8,4)               -- entered as % of trade total instead of a fixed amount
notes           TEXT
created_at      DATETIME DEFAULT NOW()
```

> **Design note:** `trade_costs` is deliberately separate from `trades` for
> maximum flexibility. Users may add any cost type with a free-form
> description and a separate amount, expressed as a fixed amount or a
> percentage of the trade total. A positive percentage is first canonicalized
> to four decimal places, and the amount calculation uses that exact value;
> `percentage_used` therefore stores the percentage actually applied. The
> resulting amount is canonicalized to six decimal places and frozen in EUR
> on creation; it is not recalculated later. Return calculations include these
> costs optionally (gross versus net returns).

#### `income_events` — Coupons and Dividends Received
```sql
id              INTEGER PRIMARY KEY
security_id     INTEGER NOT NULL REFERENCES securities(id)
account_id      INTEGER NOT NULL REFERENCES accounts(id)
cash_account_id INTEGER REFERENCES accounts(id) -- frozen historical account receiving the credit
event_type      TEXT NOT NULL               -- 'dividend' | 'coupon' | 'return_of_capital'
ex_date         DATE                        -- ex-dividend/coupon date
payment_date    DATE NOT NULL
quantity_held   DECIMAL(18,6)              -- shares held on ex_date (optional)
amount_per_unit DECIMAL(18,6)              -- dividend/coupon per unit (optional, not required in the UI)
total_amount    DECIMAL(18,6) NOT NULL     -- total gross amount received (>= 0)
currency        TEXT NOT NULL
total_eur       DECIMAL(18,6) NOT NULL
fx_rate         DECIMAL(18,8) NOT NULL DEFAULT 1
tax_withheld    DECIMAL(18,6) NOT NULL DEFAULT 0 -- withholding already applied (>= 0 and <= total_amount)
net_amount_eur  DECIMAL(18,6) NOT NULL    -- net amount in EUR
notes           TEXT

```

Optional `quantity_held` and `amount_per_unit`, gross `total_amount`,

#### `prices` — Closing Price History (Updated via CSV)
```sql
id              INTEGER PRIMARY KEY
security_id     INTEGER NOT NULL REFERENCES securities(id)
date            DATE NOT NULL
price_close     DECIMAL(18,6) NOT NULL     -- closing price
fx_rate         DECIMAL(18,8) NOT NULL DEFAULT 1

```

`source='trade'` requires `origin_trade_id`; other sources leave it `NULL`.
An automatic price thus belongs to exactly one trade: when that trade is
deleted, the service reassigns it to a surviving trade on the same day or lets
the cascade remove it if none exists. A manual or CSV upsert for the same date
becomes the authoritative data, removes automatic ownership
(`origin_trade_id=NULL`), and is not deleted with the trade. Legacy rows that
cannot be assigned to an owner with certainty are retained with
`source='legacy_trade_orphan'`.

`price_close_eur` preserves the unit conversion to six decimal places for
detail views and auditability. Position valuations do not multiply it by
quantity again: they calculate the effective EUR price from the canonical
pair `price_close × fx_rate`, then multiply by quantity, avoiding amplified
rounding from the unit column. No exchange rate other than the one frozen on
the price row is looked up or applied.

PFIM stores and imports only the closing price and its exchange rate. OHLCV
fields (`price_open`, `price_high`, `price_low`, `volume`) are **[SUPERSEDED]**
and are outside the normative contract. Their removal is **[IMPLEMENTED]** in
Alembic migration
`backend/migrations/versions/f6c4a2d8e1b9_remove_price_ohlcv.py`, which
preserves the other columns and existing rows. Apply the migration with the
precautions in §12.6, without recreating or replacing an operational database.

#### `tax_events` — Flexible Tax Ledger

`origin` declares record ownership. User input creates `manual` events; the
FIFO synchronizer may update or delete only `automatic_trade` events;
`legacy_unknown` preserves cases that a migration cannot classify reliably.
An event may reference at most one source, either a trade or income event,
and each sale may have at most one automatic event. Automatic events cannot
be edited or deleted directly. The UI uses `origin` for labels, sorting, and
actions: `manual` is “Manual”, `automatic_trade` is “Automatic from trade”, and
`legacy_unknown` is “Origin to verify”. A link does not change this
classification. Manual and legacy events retain their allowed direct actions
and, when linked, offer **Unlink source** with confirmation: it clears the
references while preserving the event and origin. Update payloads contain
only writable fields, excluding `id` and `origin`. An unexpected origin is
flagged, and the UI enables no direct actions on that entry.

Creation and editing of manual events canonicalize `gross_amount`,
`tax_amount`, and `net_amount` to six decimal places and `tax_rate` to four,
without inventing relationships among fields chosen freely by the user. The
sole exception is the gross-amount sign used by aggregation: `capital_gain`
permits a nonnegative `gross_amount` and `capital_loss` a nonpositive one.
Other types (`withholding`, `substitute_tax`, `other`) retain flexible amounts.
Automatic events additionally apply tax rounding to cents with
`ROUND_HALF_UP`, separately from technical normalization to six decimal places.

to the investment account's `reference_account_id` are therefore prospective
and do not reallocate historical cash flow. Migration `b8d1f4a7c2e9`
reconstructs the value only from the linked movement, the sole reliable
evidence; if a legacy record has no such evidence, it leaves `NULL` rather
than inferring it from the current reference. Later changes to a legacy
source without a reconstructable origin fail with an explicit conflict.

## 5. Functional Modules

### 5.1 Transactions Module (Cash Flow)

**Responsibility:** manage income and expenses, support manual entry and bank
CSV imports, and produce analysis by category, period, and account.

**Features:**

- Transaction creation, paginated listing, detail, and deletion
- Mandatory association with an account and an existing leaf category (§4.2)
- Storage of free-form tags (e.g. `#holiday2025`)
- Multiple CSV formats with configurable column mapping (see §8)
- Automatic deduplication using a hash of row content
- Implemented combinable filters: period, category, and account; two-state
  sorting by date, description, account name, category name, or EUR amount;
  pagination with at most 200 rows per page. Null/empty descriptions remain
  last in both directions
- Summaries by period and category
- **[PLANNED]** Full-text search, currency/amount/tag filters, and additional
  temporal aggregations require an explicit API contract extension

**Business Rules:**

- Every transaction has an amount in its original currency **and** a EUR
  conversion using the rate for its date
- **[IMPLEMENTED — Unreleased]** The amount cannot be zero (§4.2)
- **[IMPLEMENTED — Unreleased]** A category is required, must exist, must be a
  leaf, and must have a type consistent with the amount's sign (§4.2)
- Transfers between the user's own accounts use a dedicated workflow
  (`POST /api/v1/transactions/transfer`, §6.1): they generate two transactions
  sharing a `transfer_group_id`, negative on the source account and positive
  on the destination account, both excluded from the income statement. They
  cannot be edited individually (409; delete and recreate the pair), and
  deleting either transaction also deletes the other
- **[IMPLEMENTED — Unreleased]** Ordinary entry and CSV imports reject
  `transfer` categories; only the preceding workflow can create these
  movements (§4.2)
- Category names are globally unique under `strip().casefold()`; legacy
  duplicate names remain usable by ID but are errors in name lookups (§4.2).
  Automatic categories also require the correct type and leaf status
- Categories are hierarchical (at most two levels). A fresh installation has
  no preseeded categories; users create their own. Categories created on
  demand by system workflows carry `is_system` and remain **deletable** like
  any other category, blocked only when they have subcategories or are used
  by existing transactions (see §7.7)
- A subcategory must have the **same type** (income/expense/transfer) as its
  parent (otherwise 400). Consequently, a category with subcategories cannot
  change type (409); the subcategories would first need to be unlinked
- A category is assignable if and only if it has no subcategories; a root
  without children remains valid. Creating the first child under a used
  category is blocked with 409 while the category is referenced
- The account must be active and present on the movement's economic date.
  This also applies to CSV preview and confirmation; an inactive account
  remains viewable but its history is read-only (§4.2)

### 5.2 Portfolio Module

**Responsibility:** manage the investment lifecycle—purchases, sales, coupons,
and dividends—and calculate the current position.

**Features:**

- Security master data with type, market, currency, and ISIN (deletable when
  no trades/coupons are linked)
- Purchase/sale recording with price, quantity, date, and investment account
- Per-trade costs (fees, taxes, spreads) as separate rows, entered as fixed
  amounts **or percentages** of the trade total (immediately converted to a
  fixed amount, not recalculated if the trade changes later)
- Automatic **current portfolio** calculation (FIFO): remaining quantity and
  average cost per security
- Valuation at the latest available price in `prices` (price date always
  explicit in the UI; CSV import or single manual entry, see §5.3)
- Coupon and dividend recording with payment date, total gross amount, and
  withholding (`amount_per_unit`/`quantity_held` are optional, not required
  in the UI)
- Per-security P&L: unrealized and realized gains/losses

**Account role separation (core principle):** an `investment` account
**never** holds its own cash; it is only a container for security positions.
Every investment account has a required **reference account**
(`accounts.reference_account_id`, of type checking/savings/cash, never another
investment account), configured in Settings. It determines the cash account
for each new source, and that choice is then frozen on the record. Direct
consequences:

- Trades and coupons/dividends may be recorded **only** on `investment`
  accounts (otherwise 400), and only with a configured reference account
- Investment accounts are excluded from manual transaction entry and the
  Transfer workflow (400/absent from the relevant menus): they never have
  their own cash to transfer or record directly
- An investment account's balance (`GET /api/v1/accounts/{id}/balance`) always
  remains equal to its `opening_balance` (normally 0): its entire “value” is
  in its securities portfolio, never in its cash balance

**Automatically generated transactions (accounts interact):** every purchase,
sale, and coupon/dividend synchronizes its movement on the **cash account
frozen on creation**, resolved from the investment account's reference at
that time (never on the investment account itself). When the net amount is
nonzero, it generates a linked transaction
(`transactions.trade_id` / `transactions.income_event_id`, §4.2), so the
account balance actually reflects security movements:

- **Purchase:** cash outflow = price × quantity + any recorded costs
  (fees/taxes/spread)
- **Sale:** cash inflow = price × quantity − any costs
- **Coupon/dividend:** cash inflow = net amount (after withholding,
  `net_amount_eur`)

**[IMPLEMENTED — Unreleased] Sale cost limit.** A zero net result is not a
cash movement: a fully withheld coupon or a sale whose costs equal its
proceeds generates no `Transaction`. Adding a cost that would take total
sale costs above gross proceeds is rejected with `409 CONFLICT`: no new
`TradeCost` is persisted, and the previous cash movement remains unchanged.
A preexisting negative-net sale state is invalid and must fail explicitly
during resynchronization, without being reclassified as an expense.

Linked transactions are always normalized to **EUR** (avoiding multiple
currencies on the same account row) and use system categories consistent
with the sign: “Security Purchase” (Expense) and “Security Sale” (Income) for
trades, “Coupons and Dividends” (Income) for income events, and “Security
Costs” (Expense) for recurring portfolio costs. The transfer workflow uses
“Account Transfer” (Transfer). These categories are created on demand when
the corresponding action needs them. If users delete them (they remain
deletable like any other category), they are automatically recreated on
next use so no movement is left uncategorized.

The reference account is a **prospective** choice. On creating a trade,
income event, or recurring cost, PFIM checks that both the investment and
cash accounts are active and present on the economic date, then stores the
actual reference in `cash_account_id` on the source. Later changes to the
investment account's reference affect only new sources; synchronization and
deletion of existing ones continue using the frozen account. The rule also
applies when the net amount is zero and there is no linked transaction (§4.2).

Adding a cost within the limit above, or removing one from a recorded trade,
**recalculates** the linked transaction amount. Linked transactions cannot
be edited/deleted directly from Cash Flow (409: “managed by
Securities/Income”); changes must be made by editing or deleting the
originating trade/coupon, which in turn updates or removes the transaction.
Consistency is enforced in one direction: from the source operation to the
cash movement.

**FIFO cost calculation:**
The system uses **FIFO (First In, First Out)** as its internal convention
for matching purchases and sales: each sale consumes the chronologically
oldest purchase lot. This affects:

- Cost of sales (for realized P&L)
- Remaining weighted average cost of shares still held

FIFO matching remains global per security. Share availability is also
checked per **investment account/security** pair: before creating a sale or
deleting a purchase, all running quantities in `(date, id)` order must be
nonnegative, including future trades. A new trade follows those already
recorded on the same date; shares in other investment accounts cannot cover
a local sale. The first deficit returns 409 with investment account,
security, date, and quantity. Inconsistent history remains viewable but
blocks these two actions on the affected pair; purchases and sale deletions
retain their existing guards. This introduces no security transfers, data
cleanup, or changes to FIFO cost and the tax ledger (ADR 002).

FIFO supports valuation and continuity of PFIM's internal calculations. It
is not declared to be a tax method compliant with Italian legislation and
must not be used as proof of the tax-recognized cost basis. Tax methods and
obligations depend on the instrument, regime, and applicable legislation (§11).

### 5.3 Prices Module

**Responsibility:** manage security price and exchange rate updates through
CSV imports.

**Features:**

- Fixed-format price CSV imports (date, ticker, close, exchange rate) and
  single manual entries (specified in §7.4.1)
- **Automatic recording of trade prices:** the first trade on a date without
  a quote saves its `quote_price` in history (`source='trade'`,
  `origin_trade_id=<trade ID>`). A trade is an observed market price on that
  date; without recording it, portfolio valuation for that date uses an older
  price and could be **lower than the sale proceeds**, an inconsistency that
  made TWR unavailable (§9.3). It **does not overwrite** an existing price
  for that date: an imported or manually entered closing price is the
  official market data, while this is the price of a single execution. It
  only fills gaps. If the owning trade is deleted, the price moves to the
  first surviving trade of the day or is cascade-deleted if none remains;
  a manual/CSV upsert instead removes automatic ownership and survives
- Exchange rate CSV imports (date, currency pair, rate)
- Data preview before confirming an import (dry run: no database writes
  until confirmation)
- Internal API always returning the “latest available price” per security
- **[PLANNED]** Temporal gap reports for active securities

**Delimiter: semicolon (`;`), not comma.** A comma column separator would
split a price written with a decimal comma (`17,50`) into two columns,
misaligning the entire row. With `;`, either decimal commas (`17,50`) or
points (`17.50`) are accepted and normalized.

**Expected price CSV format (fixed, not configurable):**
```csv
date;ticker;close;fx_rate
2026-06-20;ENI.MI;14,52;
2026-06-20;AAPL;195.84;0,9145
```

`fx_rate` expresses EUR per unit of the security's currency; it may be empty
for EUR securities and is required for other currencies. OHLCV columns are
not accepted by the normative contract (§4.2).

**Expected exchange rate CSV format:**
```csv
date;from;to;rate
2026-06-20;USD;EUR;0,9145
2026-06-20;GBP;EUR;1,1632
2026-06-20;CHF;EUR;1,0521
```

**[IMPLEMENTED — Unreleased] Uniform validation.** Prices and exchange rates
must be finite, strictly positive `Decimal` values compatible with the
precision and application limits in §4.2. Manual entry, preview, and import
share normalization and validation rules. Preview and confirmation also
apply the same precedence: structure and numeric fields, including a
malformed optional exchange rate, are validated before classifying an unknown
ticker as ignored; the same row therefore produces the same counts in both
paths. SQLite `CHECK` constraints also protect writes outside the API.
System-created reciprocal rates are marked `csv_import_reciprocal` and
updated with their direct rate, while an explicit direction is not
overwritten. Inconsistent explicit pairs are rejected regardless of row
order (`R-08` closed; users remain responsible for the source's economic
reliability).

Missing or empty cells are checked before conversion; truncated rows produce
controlled row errors. Header-reading errors are handled as global errors,
without 500 responses. The APIs save valid rows with a single commit; a
global or unexpected error rolls back the entire request. Wizards instead
require an error-free preview before enabling confirmation (§8).

### 5.4 Reports Module

**Responsibility:** produce concise and analytical reports on the overall
financial position.

**Available reports:**

| Report | Contents | Frequency |
|--------|----------|-----------|
| **Net Worth** | Account balances, portfolio, and net worth; snapshots and history | Snapshot/history |
| **Income Statement** | Cash income/expenses, including security purchases and sales, net balance, and savings | Period |
| **Expense / Income Analysis** | Category breakdown; expenses also include the complete first level | Period |
| **Transfer Analysis** | Volume transferred between own accounts | Period |
| **Securities Analysis** | Positions, value, cost, P&L, and sector/industry/country classifications | Current |
| **Coupon Analysis** | Receipts by security and period | Period |
| **Costs and Taxes** | Trade costs, recurring costs, and informational tax estimates | Period |

TWR/MWR performance metrics are exposed by the dedicated endpoints in §6.7.
Report endpoints accept `format=csv` where specified by OpenAPI; net worth
history is JSON. Each tab exposes only its own export: it must not show
controls belonging to Income, Costs, or other reports. Frontend export
controls use the displayed period and make download failures clear.

**Period** reports select full months or years: the first month maps to its
first day and the last month to its last day, both inclusive in the API
contract. Multiple months, multiple years, or all history can be selected.
The **1 month** and **3 months** shortcuts select the full current month and
the current month plus its two predecessors respectively, according to the
local calendar. This rule does not apply to point-in-time/current reports
such as Net Worth and Securities Analysis, where a single date or the current
state has a distinct meaning.

Net Worth is **point-in-time**: for the requested date it includes only
accounts present within their lifecycle interval, trades already executed,
and prices no later than that date. Future dates are rejected. If an open
position has no quote on or before the date, it is not omitted: it is valued
at FIFO cost, and the response exposes `portfolio_valuation` with
`price_policy`, `cost_fallback_used`, and the affected securities. Dashboard,
snapshot, and history must explicitly flag the estimate; FIFO cost must not
be presented as a market price. The same completeness rule applies to
Portfolio, its summary, Securities Analysis, and aggregate performance: an
open position without a price does not disappear and declares
`valuation_source='fifo_cost'`. Individual-security metrics that truly require
a price remain `null` instead.

Summaries, reports, and exports traverse the entire filtered set using
internal batched keyset pagination. There is no silent 100,000-movement cap;
large datasets may take longer but must not produce truncated results
(`R-10` closed).

**Movement scopes.** The **income statement** includes cash transactions,
including security purchases and sales; it excludes both sides of transfers
between own accounts. Trade-derived transactions already contain costs:
purchases include costs and sales deduct them. Trades, costs, and tax capital
gains/losses are not added again. Income/expense classification and the
savings rate follow the sign of the EUR amount.

**Expense analysis, income analysis, and average spending for financial
runway** include economic movements and continue to **exclude**:

- **Transfers between own accounts**, both sides: money moves, while net
  worth remains unchanged
- Movements generated by **security purchases/sales**: money changes form
  from cash to instruments or vice versa

**Received coupons and recurring costs** remain included, as actual income
and expenses. **Transfer analysis** shows the *transferred volume* between
the user's own accounts (only the outgoing side, since summing both sides
would always give zero).

An **account balance**, in contrast, follows cash accounting and includes
all movements because it must match the bank statement.

## 6. REST API — Interface Contract

All APIs follow REST conventions under the `/api/v1/` prefix. The
interactive documentation generated by FastAPI at `/docs` is the source of truth
for parameters, request bodies, and response models in the current revision. The lists
below describe release 0.22.0 together with the `[Unreleased]` changes already
implemented; only the transaction list is paginated, while the other list
endpoints return arrays unless OpenAPI specifies otherwise.

Every `POST`, `PUT`, `PATCH`, and `DELETE` requires the
`X-PFIM-Capability` header. The token is obtained from
`GET /api/v1/security/capability`, exists only in process memory,
changes on restart, and is available in Swagger through **Authorize**. Host and
Origin must belong to the configured loopback boundary. This protection
reduces unintended local or cross-origin mutations, but it is not authentication and
does not authorize exposure to a LAN or the Internet (§12.6).

CORS also wraps responses from security and maintenance checks:
a browser on an allowed origin can read their status and code. Only a 403
`CAPABILITY_REQUIRED` or `CAPABILITY_INVALID` triggers token renewal and one retry;
network or maintenance errors do not retry a write. An allowed preflight
may succeed during maintenance, but the actual request remains blocked.

**No updates to transactional resources.** Transactions, trades,
categories, income events, recurring costs, CSV profiles, and forecast scenarios are
corrected by **deleting and reinserting**, rather than through PUT. This provides
one way to perform the same operation, without maintaining an update path
alongside creation or duplicating revalidation (FIFO, currency conversion,
and cash reconciliation) across both paths.

Only four resources retain PUT, each for a specific reason:

| Resource | Reason |
|---|---|
| `accounts` | the reference account is changed in Settings: without an update, the account would need to be recreated, losing its history |
| `tax-settings` | changing a rate **is** the only supported operation (§11.3): there is no "create tax rate" operation |
| `tax-events` | the tax register is explicitly flexible (§11.1): the user must be able to correct an entry |
| `securities` | it is the only way to deactivate a security, a capability assumed by `GET /api/v1/securities?only_active=true` |

```text
GET    /api/v1/health                        # Service health
```

Backup creation is disabled by default and requires
`BACKUP_ENABLED=true` plus the exact `EXPECTED_ALEMBIC_REVISION`. It uses SQLite Online
Backup with a read-only source, `.partial` staging, `integrity_check`,
`foreign_key_check`, revision verification, SHA-256, a manifest, and atomic
publication. The database and manifest form an inseparable pair that should also be
kept on separate storage; legacy backups without a manifest remain visible as
unverified.

The catalog, download, manifest endpoint, and restore selection share the same
validation: a JSON object, supported version, matching name, positive integer
size, SHA-256, nonempty revision, successful checks, and a timezone-aware
ISO timestamp. Integer fields reject booleans. The date is normalized
to UTC only in memory; hash, link, sidecar, and file-stability checks
remain active. A missing or invalid manifest makes the individual entry
unverified; it remains in the catalog with a fallback filesystem date and a
`verification_error` reason, without preventing access to the other entries. A legacy
backup can be downloaded only if its manifest is genuinely absent and the
other checks pass: a present but invalid manifest, including directories
and dangling links, blocks even a legacy download. Modern downloads
always require a valid manifest. No manifest is repaired or rewritten.

`BACKUP_COPY_TIMEOUT_SECONDS` limits the online copy loop and its retries:
the default is 60 seconds, with integer values from 1 to 600 allowed. The monotonic deadline is
checked during progress, including SQLite `BUSY`/`LOCKED` states; each attempt
waits at most 100 ms and never exceeds the configured wait. On timeout,
the API and CLI report `BACKUP_TIMEOUT` (HTTP 503), close connections, and
clean up only that invocation's staging files, without publishing an incomplete
copy or automatically retrying it. The limit does not guarantee a strict maximum
time for operating-system I/O, verification, `fsync`, or restore.

Application restore is disabled by default. It becomes eligible only
with `RESTORE_ENABLED=true`, `BACKUP_ENABLED=true`, and the
exact `EXPECTED_ALEMBIC_REVISION`. The candidate must be a modern backup
with a verified manifest, a SHA-256 confirmed by the caller, and the same revision
as the build; legacy backups and backups from another revision cannot be
restored.

The request contains a UUID `request_id`, `expected_sha256`, and the exact confirmation
`RESTORE {filename}`. The request ID makes retries with the same
parameters idempotent; the durable status (`preparing`, `committing`, `recovering`,
`completed`, `rolled_back`, or `failed`) is available from the dedicated endpoint.
During the operation, a maintenance gate rejects new requests, waits for active
requests to finish, and operates under an interprocess lock shared by the backend, backup, restore, and
offline tools.

Before the swap, a verified backup of the current database is created,
subject to the same copy limit. If it times out, the database remains in
place, the gate and lock are released, and the operation is recorded as `failed` with code
`BACKUP_TIMEOUT`. Resubmitting the same `request_id` returns 409 with the
recorded status and does not start a second copy; the status remains available.
The candidate is copied to staging on the same filesystem and checked again for
header, integrity, foreign keys, hash, and revision. The durable journal
`.pfim-restore.json` uses the phases `prepared`, `live_moved`, and `committed`: a crash
before commit rolls back to the previous database; a crash after commit
rolls the candidate forward and performs cleanup. Recovery runs under the lock
before the startup schema guard; an ambiguous state remains fail-closed without
heuristically deleting files.

The same procedure is available offline with the backend stopped through
`scripts/restore.ps1`, which refuses to run if Uvicorn holds the instance lock.
It recovers a pending journal before the schema guard, but a new
operation still requires a verifiable live database and its pre-restore
backup: it is not a disaster-recovery path for a file that is already corrupted or
incompatible. Setup, tests, and migrations must never implicitly delete, recreate, or
overwrite the operational database; the only supported replacement
is the one explicitly confirmed through the ADR 006 protocol (§12.6).

### 7.1.1 Persistent Tables and Monetary Charts

Tables displaying persistent data start **collapsed** and expand
from their headers, keeping pages with several sections compact.
The two exceptions are Cash Flow and Portfolio, which remain expanded.
Temporary previews for CSV and price imports also remain expanded and
preserve file order: they are verification steps rather than records for
later consultation.

All meaningful informational columns are sortable. Clicking a
new column applies its appropriate initial order; subsequent clicks on the
same column always alternate only between ascending and descending. Ordering is
stable and natural, without case sensitivity; missing values
remain at the bottom in both directions. Action,
selection, and inline-edit columns are not sortable.

Monetary **column charts** automatically scale the Y-axis to the data,
including zero and any negative values. There is no imposed
monetary minimum, "Minimum Y-axis scale" control, or persisted scale
preference. Other charts retain their automatic axes.

### 7.1.2 Visible Formulas on Indicators

Each indicator card (`KpiCard`, a single component shared by all
pages) can expose its **calculation formula**, shown on hover
or keyboard focus. A card with a formula is reachable with Tab;
otherwise this information would be accessible only with the mouse.

The principle is that every number reflects a calculation choice that may not be
obvious externally; making it visible allows the result to be understood and trusted.
For example, **"Account balances" and "Available cash" differ** because the
former includes every account type while the latter includes only checking accounts.
If an investment account has a negative balance, available cash can be *higher*
than the total account balance. The formula explains this distinction
and the reference-account rule is defined in §5.2.

The tooltip separates **what** is calculated (the formula line, emphasized in monospace)
from **why** (the accompanying explanation of what is included, excluded, and when
the result cannot be calculated).

### 7.2 Dashboard Page

The page opens with a **context panel** that explains in two lines what the
application does and how its three areas relate to each other (cash flow, securities and
portfolio, reports and forecasts). It helps first-time users and those
returning after several months understand where to start without having
to infer it from the menu. The main KPIs and summary charts appear below.

The dashboard is the initial view and summarizes the overall financial position:

**Featured metrics (KPI cards):**
- Total net worth (accounts + portfolio)
- Balance of all active accounts
- Current portfolio value
- Unrealized gain/loss

**Charts:**
- Income vs. expenses over recent months, **aggregated across all accounts** (grouped
  bar chart; purchases and sales included and internal transfers excluded,
  as in the income statement)
- Portfolio asset allocation by instrument type (pie chart)

The Income/Expenses chart has no implicit account or account selector: its
title and supporting text must state that it represents the overall
aggregate.

If the current valuation includes a fallback to FIFO cost, the dashboard
shows a warning listing the affected tickers and links to the Net Worth detail;
an estimate must be distinguishable from a market quote (§5.4).

**[PLANNED]** Monthly net-worth change, YTD return, net-worth history,
and upcoming events are not present on the current dashboard.
Net-worth history and performance are available on the Reports page.

### 7.4.1 Securities Page

A register of **all purchases and sales**, complementing the
Portfolio summary view: Portfolio answers "how much do I
hold now?", while Securities answers "what did I buy/sell, and when?".

**Security register section:** add form (ticker, name, type, currency,
optional ISIN) + table of existing securities, with a "Delete" action
(explicit confirmation; blocked with 409 if the security has linked trades/income events).

The selectable **instrument types** are: Stock, Bond, **Equity
ETF**, **Bond ETF**, Fund, **Commodities**. The
distinction between equity and bond ETFs is intentional: grouping them
under a single "ETF" type would obscure portfolio allocation by
hiding the difference between equity and bond exposure.

The value stored in the database remains the English identifier (`stock`,
`etf_equity`, …), while the UI **always** displays the English label, including
in tables, charts, and dropdown menus. The mapping is defined once
in `frontend/src/lib/securityTypes.ts`, keeping labels consistent between
forms and displayed data rather than exposing raw identifiers.

**Prices section:** a list of securities with the latest available price and its
date (in amber with a warning if older than 7 days), plus a small form
per row to record a new price quickly (date + value) without
preparing a CSV file, useful for an occasional update. For
bulk updates, the **"📥 Import CSV"** button opens a 2-step wizard
(§8.2): upload file → preview each row (new/update/unrecognized
ticker/error, without writes) → confirm. There is no column
mapping to configure: the format is fixed and uses `;` as the delimiter (§5.3).

**Trades section:** purchase/sale entry form (security, **investment
account**, the only selectable account type, §5.2; type, date,
quantity, price) + table of **all** trades (not filtered by security by
default) with a "Costs" column (total immediately visible without opening the
modal) and two actions per row:
- **"Costs"**: opens a modal for adding/deleting trade costs
  (commission/tax/spread/other), as a fixed amount or a **percentage
  of the trade total** (calculation shown in the preview and fixed on
  save); every change automatically recalculates the linked cash
  transaction on the historical cash account fixed for that activity (§5.2)
- **"Delete"** with explicit confirmation: blocked (409) if it would break the
  FIFO sequence of a subsequent sale (see `TradeService.delete_trade`);
  also deletes the linked cash transaction

Selectors used for writes display only active securities and investment accounts that are active and
exist on the trade date. Deactivating a security with an open
FIFO position is prohibited; once inactive, the security remains available for consultation but
accepts no trades, prices, income, or cost changes. An inactive account is likewise
read-only historical data: the costs modal and deletions are disabled as well
as protected by the backend.

**Recurring costs section:** form + table to record stamp duty, custody
fees, and account charges (§11.5). These apply to the portfolio as a whole,
rather than to an individual trade. They belong here because, like trades
and coupons, they automatically generate the cash outflow on the historical cash account fixed for that activity.

### 7.4.2 Coupons Page

Record coupons/dividends/returns of capital credited on portfolio securities

Gross and withholding labels indicate the selected currency.
The preview distinguishes the net amount in that currency from its EUR equivalent:
100 USD gross minus 10 USD withholding at an exchange rate of 0.9 displays 90 USD and 81 EUR.
Missing or invalid inputs do not become an apparent zero; withholding equal
to the gross amount legitimately produces a net amount of zero. Backend validation
and rounding remain authoritative.

### 7.5 Reports Page

Each report is selectable from a menu (tabs): Net Worth, Income Statement,
**Securities Analysis**, Expense Analysis, **Income Analysis**, **Transfer
Analysis**, **Coupon Analysis** (§7.5.1), **Costs and Taxes** (§11.6),
Backup. Parameters (period, format) are set
before rendering.

**Net Worth:** the selected snapshot shows a composition tree
that reconciles with the KPIs:

```text
Net Worth
├── Account balances
│   ├── Account A
│   ├── Account B
│   └── ...
└── Portfolio
```

Each branch uses the same point-in-time response as the totals. The tab does
not include a selector or historical chart for an individual account: it
explains net-worth composition without duplicating the account-detail API.
`GET /api/v1/accounts/{id}/history` remains available
for specific uses; the report displays the **aggregate history** of all
accounts existing at each date together with the portfolio (§6.8).

**Available cash and runway:** available cash (sum of checking accounts only,
`type=checking`, existing on the snapshot date), average monthly spending over the
last 12 months, and **months of runway** = available cash / average spending. This
indicates whether the emergency buffer is adequate, something balances
alone do not show; a warning appears below 3 months. Average spending **excludes
security purchases and transfers between the user's own accounts**: they are changes
in the form or location of money rather than expenses, and including them would sharply
reduce the apparent runway in months when investments are made.

Average spending uses **P5–P95 winsorization** on exactly 12 calendar-month
totals: it includes zero months and, for a snapshot in the
current month, data from the first day through the requested date. Thresholds are
inclusive percentiles with linear interpolation (`PERCENTILE.INC`); each
value below P5 is raised to P5 and each value above P95 is lowered to P95, then all
12 values remain in the denominator. Amounts are aggregated with their
own signs before conversion to positive spending. The same technique applies
to the average savings rate for the sample described below; monthly series and
report totals remain unchanged. If average spending is not positive,
average spending and runway are not calculable (`null`). Implementation details are in
`docs/finance-calculations.md`.

**Average savings rate:** the "Average savings" section in Net Worth
reuses `average_savings_rate_pct` and `savings_rate_months` from the income statement.
Monthly rates are `(income + expenses) / income × 100`. The average applies
**P5–P95 winsorization** only to rates for months with positive income:
it calculates inclusive **type 7** percentiles with linear interpolation
(`PERCENTILE.INC`), clamps each rate to `[P5, P95]`, and takes the arithmetic mean
of the clamped values. The entire sample is retained, without trimming:
each calculable month has equal weight, and `savings_rate_months` remains the
number of those months. Months without income are excluded; negative rates
remain in the sample, and a negative average is valid. If no months are
calculable, the value is `null`; with one month, its rate is retained.
This is not the ratio of the period's total balance to total income. Monthly rates,
amounts, and income-statement totals remain unchanged.
The section's monthly filter starts with the full history and changes only
this indicator, without changing the net-worth snapshot or performance.
The sample follows the selected period without imposing a 12-month window.
The average is also affected by purchases and sales included in the income statement.

**Net-worth history:** stacked area chart with **account balances** and **portfolio
value**, plus a line for total **net worth**. Account balances alone
fall when securities are purchased because cash is converted into instruments;
showing balances alongside portfolio value makes this change in the form of assets
visible without implying a decline in net worth.

The snapshot shows a warning for securities valued at FIFO cost. The
history indicates how many points contain this estimate and which tickers are
affected, using the metadata returned for each date (§5.4).

A **"Securities portfolio growth"** section displays aggregate return
metrics (§9.3, §9.4), divided into two blocks:
- **Annualized**: annual TWR, annual MWR/IRR, annual Total Return; compounded
  rates (CAGR, §9.5.1), comparable across periods of different lengths
- **Cumulative over the full period**: cumulative TWR, cumulative Total Return,
  income received

It also includes a detail table for each security and an explicit indication of the
reference period (years and days since the first trade). MWR appears
only among annualized metrics because it is **already** an annual rate by construction
(§9.5.1). TWR and MWR are shown together deliberately because they answer two
different questions: how the portfolio itself performed (comparable to an
index), and how the capital performed given the timing of its actual
contributions. They should be read together. They are `null` (displayed as "—")
when there are no recorded trades or no calculable initial value.

**Securities Analysis:** a snapshot of the **current** portfolio (§6.8
`/reports/securities-analysis`). The Securities page records purchases and
sales; this report considers only current holdings: a security bought and
then sold in full does not appear.
Contents:
- KPIs: portfolio value, number of open positions, instrument types
- **Concentration**: weight of the largest security, largest 3, and largest 5, plus
  **effective holdings** = 1/Σw² (inverse of the Herfindahl index), showing how
  many *equally weighted* securities the portfolio is equivalent to. With 10 securities,
  one of which accounts for 80%, the value remains close to 1: the portfolio behaves
  almost as if it held a single security despite containing ten. A warning appears
  when the largest security exceeds one third. The value ranking identifies *which*
  securities are largest; this section indicates *how much* the portfolio depends on them
- **Currency exposure**: breakdown by currency, highlighting the portion
  exposed to exchange-rate changes. The app normalizes everything to EUR, but exchange-rate risk
  remains and would not be visible elsewhere without this view
- **Sector, industry, and country**: three scalar breakdowns of open
  positions by current value, percentage, and position count. Empty fields
  are grouped as "Not specified". For ETFs these describe the label
  assigned to the security, not a weighted analysis of its underlying holdings
- **Pie chart** of allocation by instrument type, plus
  detail showing value, percentage, and number of securities per type
- **Top 10 securities by value**
- **Top 10 gainers** and **Top 10 losers**, sorted by percentage
  change (only positions with gains and losses, respectively)

Amounts, allocation shares, and gain/loss percentages are expressed in EUR
(§9.8). Gain/loss percentages compare converted value and cost and therefore
also reflect exchange-rate effects on foreign-currency securities.

**Expense Analysis / Income Analysis / Transfer Analysis:** all three tabs
share the main statistics and the `CategoryAnalysisReport` response
schema; Expense Analysis adds top-level category detail views:
- **Whole-month** selector (From month/To month), annual shortcuts, and
  "All history"
- **Pie chart** of the category breakdown
- **Bar chart** of month-by-month trends
- **Top 10 categories** (with percentage of the total)
- **Top 10 transactions**

**Expense Analysis** additionally includes a breakdown of **all** top-level
categories and an **Expenses in category** section: selecting a root
shows a pie chart of the totals for all descendant categories with activity and
a list sorted by descending net spending, with **8 entries per page**.
The pie chart includes every entry, including those on subsequent pages.
Categories used directly, including a root without subcategories,
are counted only once. The JSON `by_category_detail` is complete
and contains `top_level_category_id`; the older `by_category` retains the Top 10.

Expenses are net of refunds within each category. Zero or net-refund totals
remain in the list, but only positive net expenses form the pie
slices and the denominator for their percentages. When refunds exist, an explicit
note explains the difference from the net total. Changing the category or period

## 8. Import/Export and Data Integration

### 8.1 Import Online Banking Transactions (CSV)

Each bank uses a different CSV format. The system supports **configurable mappings per bank**.

Each upload is read in chunks and rejected above 5 MiB by default; the parser
stops above 100,000 rows. Invalid UTF-8, a delimiter that is not a single
character or is a newline, malformed CSV, and invalid numeric values produce structured PFIM
errors; exceeding the limits returns `413 PAYLOAD_TOO_LARGE` without
writes. The limits are configurable but cannot be removed without
reassessing memory usage and execution time (`R-11`).

**Import flow (4-step wizard):**

1. **Upload file** — drag the CSV or select it from the filesystem
2. **Select profile** — choose a saved profile (§7.7, `csv_import_profiles`
   table, managed in Settings) or "Custom"
3. **Map columns** — form with mappable fields (date, description,
   amount, category), delimiter, date format, decimal
   separator, and default currency; the preview is generated in the next step
4. **Preview and confirm** — table showing the rows to be imported,
   highlighting duplicates and errors (blocked rows). The response retains
   global counts while paginating details: 200 rows by default, maximum 500

**Profile persistence:** each profile is a row in the
`csv_import_profiles` table (§4.2), with list, create, and delete operations exposed at
`/api/v1/csv-import-profiles` (§6.10) and managed in Settings.
No CSV import profiles are seeded in a fresh installation; users create the profiles they need.

**[IMPLEMENTED — Unreleased] Category mapping and validation.**
`category_column` is required when creating a new profile and starting a
preview or import. Legacy profiles with a `NULL` field remain readable and
selectable, but the wizard requires the mapping to be completed in step 3 before
continuing. The value read from the CSV is resolved by name using
`strip().casefold()`, matching exactly one existing leaf category (§4.2).
An empty column or cell, a nonexistent, ambiguous, or non-leaf category, a
zero amount, an inconsistent sign/type combination, or a `transfer` category makes the row
ineligible for import, with the same
result in preview and confirmation. The system does not create categories or reconstruct
transfers from a single CSV transaction: transfers can be recorded only
through the dedicated flow in §5.1.

Missing required cells in truncated rows become row errors
before dates/amounts are converted; they are not replaced by zero or the
text `None`. The bank description value remains optional, including
when it is missing because the row ends before the mapped column. The header
must still contain the profile's columns. Missing, duplicate,
or malformed headers and unreadable CSV structure produce controlled global errors.
The APIs import valid rows in a single commit; a global or
unexpected error rolls back the entire request. The wizard enables confirmation only if
there are no errors anywhere in the preview, including pages that are not displayed.

**Deduplication:** each imported row generates a hash
`SHA256(account_id + date + amount + description)`. Rows whose hash already
exists are flagged as duplicates and skipped by default.

The **account** is part of the row's identity: the same activity imported
into two different accounts represents two transactions. Including the account in the
hash prevents the second transaction from being silently discarded (`import_hash` is UNIQUE across the table).
The amount is normalized to its stored precision before hashing:
six decimal places. Thus, `-1.5` read from the CSV and `-1.500000` read back
from the database remain the same amount.

Comparison covers both rows already in the database and those
**already encountered in the same file**: two identical rows in the same CSV
are an ordinary case and must be recognized before both are written.

For this reason, `POST /api/v1/transactions/import/preview` also requires `account_id`:
which rows are duplicates depends on their destination.

The wizard uses an immutable snapshot of the file, profile/mapping, account,
currency, and exchange rate for preview, subsequent pages, and confirmation. Changing these
values or returning to earlier steps invalidates the preview; stale responses
are ignored. Relevant controls are disabled during requests,
and a synchronous guard prevents duplicate confirmations. The backend still
revalidates at import time: the preview does not reserve data.

### 8.2 Import Security Prices

- **Fixed** CSV format (not configurable like bank-transaction imports),
  with `;` as delimiter: `date;ticker;close;fx_rate`. `date`, `ticker`, and `close` are
  always required; `fx_rate` is required for non-EUR securities and blank or
  omitted for EUR securities. Decimal commas or points are accepted (§5.3)
- **Does not use the column-mapping profiles** configurable in Settings: those apply
  only to bank-transaction imports (§8.1), whose format varies by bank
- Ticker matching: exact ticker first, then ISIN (if the `ticker` column
  instead contains a valid ISIN)
- UI: 2-step wizard in Securities → Prices ("📥 Import CSV"): upload the file, then preview
  each row (new/update/unrecognized ticker/error) before confirming
- Preview and confirmation share parsing, matching, and validation; prices and
  exchange rates must be finite, strictly positive, and within numeric limits. The
  preview is paginated at 200 rows by default, maximum 500, with global counts
- The preview simulates the entire file in order before pagination, using
  the `(security_id, date)` key after matching: a security's ticker and ISIN
  share the same state. Only valid, recognized rows update it;
  **the last valid row wins**. A later invalid row does not remove
  the earlier valid one. Overwritten rows identify the final row and
  applied values, even when occurrences are on different pages
- Import performs an upsert by (security, date), retaining ownership of
  imported prices. Two valid rows for the same initially absent key count
  as 1 new and 1 update, in both preview and confirmation. The preview does not reserve
  the database; confirmation revalidates the state
- Missing or malformed required cells are row errors; `fx_rate` remains
  optional for EUR and required for foreign currency. A structural
  or numeric error takes precedence over an unknown-ticker classification (§5.3).
  The wizard enables confirmation only for an error-free preview; the APIs
  retain single-commit saving of valid rows (§8.1)
- Post-import report: prices imported (new), updated, unrecognized securities, errors

### 8.3 Import Exchange Rates

- CSV format (see §5.3)
- If the EUR→USD rate is available but USD→EUR is not, the system automatically
  calculates the reciprocal and marks it `csv_import_reciprocal`; updating the
  direct rate also updates the automatically generated reciprocal without overwriting
  an explicit value. Two explicit directions that are not reciprocal within tolerance are
  rejected
- Date, currencies, and rate are required. Missing or malformed cells
  produce row errors; the response retains its counters and adds
  `row_errors: [{row_number, column, message}]`, displayed in Settings.
  Numbering starts at 1 for the first data row; `column` can be `null`
  for whole-row errors. `errors` counts invalid rows even when a
  row has multiple messages. Single-commit and global-rollback behavior follow §8.1
- The FX policy differs from price upserts: multiple valid rows for the same
  `(date, from, to)`, even identical ones, are all rejected as duplicates
  of that direction; the last occurrence does not win

### 8.4 Export

The endpoints in §6.8 exposing `format=csv` support CSV export. There is
no implemented requirement for exporting every main view; any
new exports must define their columns, applied filters, and value formats
before being added.

## 9. Financial Calculation Engine

The modules in `backend/app/finance/` are pure Python functions, with no
DB or HTTP dependencies, independently testable and based on `Decimal`.

The performance contract distinguishes two independent dimensions:
`income_basis=net|gross` for income and
`cost_basis=exclude|include` for costs. Each response declares the effective
basis of each metric in its metadata; “gross” or “net” must not be inferred
from a single boolean (§6.7).

### 9.1 Current Position (FIFO)

```python
def calculate_position(trades: list[Trade]) -> Position:
    """
    Calculate the current position for a security using FIFO.
    Return: remaining quantity, remaining lots with their cost basis,
    weighted average cost, total invested, and realized gain/loss.
    """
```

**FIFO algorithm:**
- Maintain a chronologically ordered queue of purchase lots
- Each sale consumes lots from the head of the queue
- Realized gain/loss is `(sale price - FIFO cost basis price) × quantity`

`calculate_position` is the generic primitive operating on the `price` field
of the supplied object. Services do not assume that `trades.price` is in the
security's currency: `calculate_position_native` adapts `quote_price`, while
`calculate_position_eur` allocates the frozen value `total_eur / quantity`
to each unit for every aggregation. Fully consuming a lot therefore
reconstructs exactly the total used by the cash transaction and does not
amplify the rounding of the unit `price_eur` to six decimal places. Quantity
and the check against short selling are currency-independent invariants.

This is an internal valuation convention. The result does not claim tax
compliance and does not replace the method applicable to the user's tax
regime and instrument type (§11).

### 9.2 Simple Return

```
R_simple = (P_current - P_cost_basis + Dividends) / P_cost_basis
```

The income basis and cost basis can be selected separately. Recurring costs
are not allocated to individual securities: the response declares
`not_allocated_to_security` instead of inventing an allocation.

### 9.3 Time-Weighted Return (TWR)

TWR removes the effect of cash flows (purchases/sales), measuring the “pure”
performance of a security or portfolio:

```
TWR = [(1 + R₁) × (1 + R₂) × ... × (1 + Rₙ)] - 1
```

where each `Rᵢ` is the return for the subperiod between two consecutive flows.

**Implementation:** the engine calculates the portfolio value before and
after each cash flow (purchase/sale), divides the history into subperiods,
and chains their returns.

For each date, with `P` the value of securities before trades, `G` purchases
minus sales, `I` income on the selected gross/net basis, and `C` included
costs (zero when excluded), the flow is `G - I + C`, the value before the
flow is `P + I - C`, and the value after the flow is `P + G`. Adjustments
are separate for each cost mode. With capital of 100 already invested and
an unchanged price, subsequent income of 10 produces a 10% return; with a
cost of 5 on the same date as the income, it produces 5%; a cost of 10 alone
after opening produces -10%.

**Start of the period.** The period starts with the **first trade**, not the
first flow of any kind: flows also include coupons and dividends, and income
dated before the first purchase would open the period on an empty portfolio
— zero initial capital and undefined TWR. Flows before the first trade are
discarded because they cannot have moved a portfolio that did not exist.
Without this rule, a typo in a coupon date could make the metric unavailable
for the entire history.

When the period opens a position, the initial factor is
`(V0 + I0) / (V0 + C0)`, with `V0` the value after the initial trades;
subsequent periods start from `V0` without counting opening flows again.
A purchase of 100 and an initial cost of 5 produce
`100/105 - 1 = -4.7619%`. If the selected period starts with an already-open
position, the initial basis is instead `P`, and flows on the initial date
are included in the chained return.

**When it cannot be calculated** (the report returns `null`, the UI shows “—”):
- No recorded trades, or a zero portfolio value at the first trade
- The opening value of a subperiod is not positive: this happens when a
  withdrawal exceeds the portfolio valuation on that date, typically because
  the latest preceding quote is much lower than the sale price. If no quote
  exists on or before that date, the position is included at FIFO cost
  instead of being omitted. Since v0.15.0, each trade also records its own
  price (§5.3), reducing this case for new data without treating an estimate
  as a quote
- The entire portfolio reaches zero at the end of a day within the period,
  even if it is subsequently reopened: the result remains `null`. Closing a
  single security does not empty the portfolio if other positions remain
  open; a sale and repurchase on the same day remain aggregated, without
  reconstructing intraday activity

### 9.4 Money-Weighted Return / IRR

MWR accounts for **when** capital was invested. It is calculated as the
internal rate of return (IRR) of the cash flows:

```
0 = -C₀ + Σ (Fᵢ / (1 + IRR)^tᵢ) + V_final / (1 + IRR)^T
```

where `C₀` is the initial investment, `Fᵢ` are intermediate flows
(reinvestments, withdrawals, dividends), and `V_final` is the current
portfolio value.

**Implementation:** an internal XIRR calculation using `Decimal` and
bisection, irregular dates on a 365-day basis, a tolerance of `1e-7`, and a
maximum of 200 iterations. The search interval is [-99.99%, 1000%]. Flows
are first summed exactly by date using `Decimal`, and zero totals are
removed: at least two remaining dates are required, with at least one
negative flow and one positive flow. Flows of -100/+100 on the same day do
not determine a rate (`null`); one year apart, they yield 0%. If no root can
be found within the interval, the metric cannot be calculated. The engine
does not use `numpy_financial`, whose IRR assumes regular periods.

### 9.5 Total Return

Includes **coupons and dividends** in the return calculation:

```
Total Return = (V_final - V_initial + Net_dividends + Net_coupons) / V_initial
```

Available with a gross or net income basis and with costs included or
excluded, according to the explicit dimensions of the contract. Withholding
taxes are subtracted only on the `net` basis.

### 9.5.1 Annualization (CAGR)

Each **cumulative** return (TWR, Total Return) is accompanied by its
corresponding **compound annual** rate so that periods of different lengths
can be compared — +20% in 6 months and +20% in 5 years are very different
results:

```
R_annual = (1 + R_cumulative)^(365 / period_days) - 1
```

The period runs from the **first recorded trade** to today.

**MWR/IRR must not be annualized**: the XIRR formula (§9.4) discounts flows
on an annual basis (`days/365`), so it already returns an annual rate.
Annualizing it a second time would be a calculation error.

Annualization is undefined if the number of days is not positive, the return
is nonfinite, or the cumulative return is ≤ -100% (capital reduced to zero).
A power overflow or a nonfinite/unrepresentable result likewise makes only
that metric `null` (“—” in the UI): the cumulative return, net worth, and
other metrics remain available. For example, +1000% in one day preserves
the cumulative return in a valid HTTP response, even without a
representable annualized return. The formula and ordinary numerical
behavior remain unchanged; no arbitrary percentage cap is imposed and no
error is replaced with zero.

### 9.6 Yield on Cost (YoC)

For each security that distributes coupons/dividends:

```
YoC = Net_income_last_12_months / TOTAL_cost_basis × 100
```

Both terms are **position totals**, never values for a single unit: income
is the total received, and the cost basis belongs to the entire position
that remains open (`Position.total_invested`, §9.1). Dividing a total by the
*average* cost per unit multiplies the result by the number of units held.

### 9.7 Current Yield

```
Current Yield = Net_income_last_12_months / TOTAL_market_value × 100
```

The same consistency requirement applies as in §9.6: the denominator is the
value of the entire position (quantity × price), not the unit price.

“Last 12 months” means 365 days, the same window used by every other
*trailing* indicator in the system: the inclusive window
`[today − 364 days, today]`. Today and today−364 are included; today−365 and
tomorrow are excluded, regardless of leap years. The definition resides in
a single place in the code (`app.finance.periods.trailing_year_start`),
with both duration and comparison together: sharing only the duration had
not been enough to make the two reports that use it respond consistently.

### 9.8 Multi-Currency Normalization

All aggregate metrics (the overall portfolio) are calculated in EUR.

**Conversion on entry.** Every amount entering the system declares its
currency and, if it is not euros, the exchange rate at the time of the
transaction. The amount and rate are first canonicalized to six and eight
decimal places respectively (§4.2); the euro value of flows is then
calculated, canonicalized to six decimal places, and saved immediately,
once only. The rate is required: without it, the entry is rejected (400)
rather than partially accepted.

Consequently:
- Historical flows remain converted at the rate on their date, which is the
  rate actually applied at the time;
- Current valuation uses the `price_close × fx_rate` pair declared on the
  latest available price. This multiplication precedes multiplication by
  quantity and does not reuse the already-rounded unit `price_close_eur`;
- No calculation looks up an external rate at runtime, so there is no
  “rate not found” case. Flows sum frozen euro values; valuations instead
  reconstruct the EUR price from the pair frozen on the same price row.

The native value at the declared precision remains stored alongside the
converted value: the interface shows native values in detail rows and euros
in all totals. Decimal places beyond the scale are not distinct data to
preserve: they are resolved deterministically with `ROUND_HALF_EVEN` before
every calculation and write.

Accounts are allowed **only in euros**: their balance is the sum of already
converted transactions, and a foreign-currency account would have its
balance and opening balance in two different units. A foreign-currency
transaction is recorded on a euro account by declaring the currency and
exchange rate on the transaction itself.

The `fx_rates` table is no longer required for calculations: it remains an
optional archive for **suggesting** a plausible exchange rate in forms
(`GET /api/v1/fx-rates/suggest`).

> `docs/multi-currency.md`.

## 10. Forecasting Module

### 10.1 Approach

The forecasting module uses a scenario-based **parametric simulation model**.
It does not use stochastic models (Monte Carlo), but three deterministic
projections: base, optimistic, and pessimistic.

### 10.2 Scenario Input

`horizon_years` accepts values from 1 through 50 inclusive.
`starting_net_worth="auto"` reads actual cash and portfolio values separately;
an explicit number is instead treated entirely as initial cash. Finite
numbers, including numeric strings, zero, and negative values, are accepted.
Arbitrary/empty text, booleans, `null`, `NaN`, and infinity produce 422 for
new scenarios. `monthly_savings_to_invest: null` selects automatic savings
(income minus expenses); a numeric amount makes savings explicit.

Before execution, the saved parameter JSON is revalidated against the same
schema, before conversions and resolution of automatic values. An invalid
legacy record remains viewable and produces 400 with the scenario ID and
invalid fields, without being modified. Comparison validates all selected
scenarios before running them: if one is invalid, it identifies which
scenario prevents the combined response; it does not present partial
results. Previously tolerated historical JSON properties remain accepted.

```json
{
  "name": "Base Scenario 2026-2041",
  "base_date": "2026-06-01",
  "horizon_years": 15,
  "parameters": {
    "starting_net_worth": "auto",
    "cash_flow": {
      "monthly_income": 4500,
      "monthly_expenses": 3200,
      "income_growth_rate_annual": 0.02,
      "expense_growth_rate_annual": 0.025,
      "monthly_savings_to_invest": null
    },
    "portfolio": {
      "expected_annual_return": 0.07,
      "return_optimistic": 0.10,
      "return_pessimistic": 0.04
    },
    "contributions": [
      { "date": "2028-01-01", "amount": 20000, "label": "Severance payment" },
      { "date": "2030-06-01", "amount": -15000, "label": "New car" }
    ]
  }
}
```

Returns are total returns and include distributions assumed to be
reinvested; there are no switches to separate them from price. Rates are
fractions: `0.07` means 7%, and `0.02` means 2% annual income growth.

### 10.3 Projection Output

Each year corresponds to the interval **(previous anniversary, current
anniversary]**. Positive or negative extraordinary contributions are added
in full to the portfolio at the end of the interval, after the annual
return and without any return during that year. The base date already
represents initial net worth: contributions on or before the base date and
those beyond the horizon are excluded. Each later contribution within the
horizon is included exactly once. With a base date of 2026-06-01, the first
interval includes both 2026-09-01 and 2027-06-01.

Anniversaries preserve the original month and day, including the 29th,
30th, and 31st. Only February 29 becomes February 28 in non-leap years and
returns to February 29 in the next leap year, because each anniversary is
calculated from the original base date. The convention is the same for all
three variants, and the form flags contributions outside the projection
without changing the saved contributions.

For each year in the horizon, the system produces:

- Estimated investment portfolio value
- Estimated balance of cash accounts
- Estimated total net worth
- Annual cash flow (income - expenses)
- Estimated annual income and expenses

Values are calculated for all three scenarios. The trajectories represent
user-defined assumptions, not probability or confidence intervals.

### 10.4 Visualization

- Area chart with three lines (optimistic / base / pessimistic)
- Comparison of multiple saved scenarios: series keys are `scenario_<id>`,
  and names are labels only. Duplicate names add the ID in the legend and
  tooltip, for example `Retirement (#12)`; names such as `year` or
  `__proto__` do not alter other series. Different horizons remain distinct:
  a shorter line ends without artificial zero values
- **[PLANNED]** Detailed annual table
- **[PLANNED]** Automatic milestones already returned by the backend but not
  yet displayed in the UI

## 11. Tax and Fee Management

### 11.1 Flexibility Principle

The system **does not** implement or certify Italian tax law. Calculations
are configurable informational estimates and do not turn FIFO or other
internal methods into recognized tax methods. The structure allows users to:

1. Record trade costs, recurring costs, withholding taxes, and tax events
   with descriptions and notes
2. Link a cost to its trade or account and, for a tax event, optionally to a
   single trade or income event
3. Calculate aggregate totals and estimates based on configured rates
4. Export the Costs and Taxes report to support verification

Flexibility does not allow a sign that would reverse the meaning in reports:
when `gross_amount` is present, `capital_gain` requires it to be nonnegative
and `capital_loss` nonpositive. No additional sign constraint is imposed on
other types; their amounts remain editable according to the semantics
chosen by the user.

**[IMPLEMENTED — Unreleased] Explicit ownership.** Create and update enforce
mutual exclusion between `related_trade_id` and `related_income_id` and
validate references. `origin` distinguishes manual events, automatic sale
events, and uncertain legacy events: the synchronizer changes or deletes
only its own `automatic_trade` events, while manual or `legacy_unknown`
references protect the source from ambiguous deletion with an explicit
conflict. Migration `d4e8f2a6c1b9` classifies only unambiguous cases and fails
before changing the schema if links are ambiguous (`R-07` closed).

UI labels and actions follow `origin`, not the presence of a link (§4.2).
Linked manual and legacy events can be deleted or unlinked directly with
confirmation; **Unlink source** preserves the entry and its origin while
clearing the references. Automatic events remain managed by their source
and protected by the backend; an unexpected origin enables no UI actions
and is not reclassified.

### 11.2 Preconfigured Cost Types

Current contracts distinguish the origin and semantics of a cost:

| Type | Applies to | Description |
|------|------------|-------------|
| `commission`, `tax`, `spread`, `other` | `trade_costs` | Options offered by the UI; the API also preserves custom descriptions |
| `stamp_duty`, `custody_fee`, `account_fee`, `other` | `portfolio_costs` | Allowed recurring cost types |
| `tax_withheld` | `income_events` | Numeric withholding field, not a `cost_type` |
| `capital_gains_tax`, `withholding_tax` | report output | Summary labels generated by the calculation, not ordinary form options |

The report also recognizes `stamp_duty` and `capital_gains_tax` on
legacy/custom trade costs and classifies them as taxes. Free text does not
imply that every label has automatic tax semantics.

### 11.3 Configurable Rates

In **Settings > Taxes**, users can view and edit the initial rates:

```
Capital gains substitute tax:        26.00%  [editable]
Italian dividend withholding:       26.00%  [editable]
US dividend withholding (WHT):       15.00%  [editable]
Securities stamp duty:                0.20%  [editable]
```

Each value is a canonical percentage with four decimal places in the closed
interval 0–100. Validation also applies in the service and on reading, not
only in the form: a negative rate or a rate above 100% cannot feed a tax
estimate.

### 11.4 Tax Position — A Single Calculation

**There is no separate “tax ledger” report.** Its aggregates duplicated those
in “Costs and Taxes” (§11.6), with one value diverging: everything now lives
in a single tab with a single calculation source.

The period's tax position is exposed by
`GET /api/v1/reports/costs-analysis` in the `fiscal` field and is built as
follows:

```
realized capital gains
− realized capital losses       (offset)
= taxable base
× tax rate (§11.3)
= estimated gross tax
− tax already withheld and recorded on a sale
= estimated tax still due       (never negative)
```

**Capital losses offset capital gains**: the rate applies to the net amount,
never to each gain separately. Applying it event by event ignores losses
and produces a much higher amount than due — for +1,000 and −600, it would
produce 260 instead of 104.

The `tax_amount` field on each `tax_event` remains a **detail** (gross tax on
that gain, before offsetting) and must never be summed across events. On
automatic events, it is rounded to the cent with `ROUND_HALF_UP` before
persistence, and the net amount subtracts the already-rounded value.

Before applying this cent-level tax rule, the taxable base and rate are
canonicalized to six and four decimal places respectively. An automatic
delta that becomes zero at six decimal places does not represent a
persistable event: the corresponding event is omitted or removed.

Taxes recorded as costs of type `tax` or `capital_gains_tax` **on a sale**
count as “already withheld.” Stamp duty does not: it is a tax on assets,
and subtracting it from the estimate would reduce the amount for the wrong
reason.

**Declared limitations:** offsetting applies only within the queried period;
there is no carryforward of losses between periods, nor any distinction
between income categories, tax regimes, instruments, or intermediaries.
The result is therefore not a compliant tax position and must not be used
directly in a tax return.

⚠️ **Required report disclaimer:** *“This report is generated for
informational purposes. Tax information must be verified by a qualified
professional before filing a tax return.”*

It provides:

- Total capital gains realized in the year
- Total capital losses realized in the year
- Net balance (gains/losses offset)
- Estimated applicable tax (based on configured rates)
- Trade-by-trade details
- Total withholding taxes on dividends/coupons

### 11.5 Recurring Portfolio Costs

The `portfolio_costs` table holds costs that apply to the portfolio as a
whole and recur over time (stamp duty, custody fees, deposit account fees),
unlike `trade_costs`, which are tied to a single trade.

Each cost is recorded on an **investment account** and, as with trades and
coupons (§5.2), automatically generates its linked cash outflow on the
**cash account frozen at creation**, initially resolved from the reference
account — using the system category “Security Costs,” which cannot be
edited from Cash Flow. This prevents net worth from being overstated and
maintains a single rule for all economic transactions.

These costs are recorded under **Securities → Recurring costs**.

### 11.6 Costs and Taxes Report

Replaces the former tax ledger as a tab in Reports. It answers the question
“how much drag does my investment activity create, and how much does it
affect performance?” Default period: **all history**. The shared selector
supports whole months, month ranges, and calendar-year shortcuts; the same
interval is applied to the CSV export.

**Block 1 — Realized result (gross):** capital gains, capital losses, the
net offset result, and gross coupons/dividends. Capital losses **are not**
a cost: they are market losses and belong here because they provide the
reference against which to interpret costs.

**Block 2 — Costs incurred**, in three groups:

| Group | Contents | Source |
|-------|----------|--------|
| Taxes | capital gains tax, coupon/dividend withholding | actual if recorded, otherwise estimated from the rate |
| Operating costs | commissions, spreads, and other purchase/sale costs | `trade_costs` |
| Recurring costs | stamp duty, custody fees, and account fees incurred | `portfolio_costs` |

**Rule against double counting.** Each item is labeled **actual** or
**estimated**:
- `tax` or `capital_gains_tax` costs recorded on sales are capital gains
  taxes already withheld and reduce the remaining estimate, never below zero.
- `stamp_duty` is classified as a tax but does not reduce the capital gains
  estimate: it applies to assets and has a different basis.
- Estimated stamp duty (current portfolio value × rate from §11.3) is
  separate current information: it appears only if the period includes today
  and there is no actual `stamp_duty` cost in the current year. It is not
  included in the period's groups, totals, net result, or cost ratios.
- Coupon withholding taxes are always actual amounts: they come from the
  user-entered `tax_withheld` field.

**Block 3 — Impact on performance**, four views:
- **% of average invested capital**: how many euros of costs for each €100
  of average daily FIFO cost basis in the period
- **% of gross result**: how much of the gain was eroded (`null` if the
  gross result is not positive)
- **Annual cost ratio**: costs / average daily portfolio value, annualized
  using the period's inclusive day count; it can be compared with an ETF's
  TER only as an order of magnitude
- **Return drag**: difference in percentage points between TWR before and
  after costs (§9.3)

The report exposes `average_invested_capital`, `average_portfolio_value`,
and `period_days`. Realized results, taxes, costs, averages, and TWR share
the same effective interval; a `date_to` beyond today is capped at today,
and the response declares the date actually used in the calculation. A
future start date is rejected. Compared tax amounts are rounded to the
cent with `ROUND_HALF_UP`.

**TWR after costs** incorporates drag both in the flows and in values before
the flows, while keeping the securities' value after the flow identical
(§9.3). The opening day applies the factor `(V0 + I0) / (V0 + C0)`, so the
initial commission counts exactly once. Coupon withholding taxes are
already deducted in both variants because `net_amount_eur` is net by
definition.

⚠️ **Disclaimer:** *“Amounts marked as 'estimated' are calculated from the
configured rates, not from tax documents. Verify them with a qualified
professional before filing a tax return.”*

## 12. Development Principles

### 12.1 Sound Abstraction

- **Routers:** handle HTTP and error conversion; reusable rules remain in
  services or financial modules.
- **Service layer:** orchestrates repositories, ORM queries, and units of
  work on the SQLAlchemy `Session`. The session dependency is explicit and
  tested.
- **Repositories:** concrete classes for reusable queries, based on a generic
  helper; no nonexistent in-memory abstraction is assumed.
- **Finance engine:** pure functions without side effects or DB/HTTP
  dependencies.
- New abstractions are introduced when they remove actual duplication or
  define a testable boundary, not as a nominal requirement.

### 12.2 Consistency

- Endpoints declare Pydantic schemas wherever a structured contract exists
- API dates always use ISO 8601 (`YYYY-MM-DD`)
- Schemas and the finance engine use `Decimal` for amounts and rates;
  writers explicitly canonicalize scale and domain before calculations and
  `NUMERIC` persistence (§4.2)
- Currencies always use ISO 4217 codes (`EUR`, `USD`, `GBP`, `CHF`)
- Python, SQL, TypeScript, and JSON APIs use `snake_case` contract names
- The EUR values of flows are frozen on entry; market valuations use the
  canonical price and exchange rate frozen on the same row, without looking
  up external data (§9.8)

### 12.3 Efficiency

- Repeated queries and N+1 queries must be measured and removed from critical
  paths
- The transaction list uses server-side pagination (default 50, maximum
  200); other lists are arrays in the current release
- Aggregate calculations (TWR, IRR) run only on explicit request, not in the
  background
- Indexes and constraints are defined by models and migrations, not by this
  descriptive list; the schema-to-model test must detect drift
- TanStack Query on the frontend handles data caching with selective
  invalidation

### 12.4 Effective Documentation

- This specification contains invariants and product decisions; OpenAPI
  contains the exact HTTP contract; Alembic contains the deployed schema;
  README and `docs/setup.md` contain operational commands (§Scope and
  Sources of Truth).
- Each change must update the affected documents within the same cycle:
  `CHANGELOG.md` for the released change, this specification for requirements
  and statuses, `docs/` for procedures/formulas, and an ADR for irreversible
  decisions or decisions with significant alternatives.
- Future descriptions remain `[PLANNED]`; an item becomes `[IMPLEMENTED]`
  only after code, migration if needed, and tests are complete.
- Docstrings and comments explain formulas, invariants, and non-obvious edge
  cases; ceremonial text is not required for every function.
- Each release verifies the application version, Markdown links, referenced
  endpoints, CSV formats, and project structure.

### 12.5 Testing

| Level | Framework | Status/goal |
|-------|-----------|-------------|
| Finance and service unit tests | pytest | Implemented; formulas, lifecycle, and domain rules |
| API/migration/concurrency integration tests | pytest + httpx2 | Implemented; includes schema, fail-closed migrations, backup/restore, and separate SQLite writers |
| Frontend | Vitest | Utilities, API client, CSV controllers, and static React rendering: coupon fields, tax actions, price preview state, FX errors, and income KPIs; scenario comparison covered by pure utilities |
| Browser E2E | manual smoke test on an isolated database | **[PLANNED]** automate critical flows |

This version of the specification does not define a percentage coverage
threshold: it must be established using risk-based criteria, not declared
achieved without automated measurement. Test totals are a snapshot rather
than a fixed requirement; after each change, a new complete run provides
the evidence.

Static React rendering verifies presentation conditions using simulated
data; it is not equivalent to a complete browser session or an automated
E2E test.

**[PLANNED]** Extend component and API hook tests to interactions and
loading/error/empty states that remain uncovered, and automate browser E2E
before considering frontend integration covered.

### 12.6 Operational Data Safety

- Databases in `data/`, SQLite sidecars, and backups may contain real
  financial data: they must not be deleted, renamed, overwritten, or used
  as test fixtures.
- Tests and checks must use temporary or in-memory databases explicitly
  isolated from the operational path. An audit using representative data
  uses only a separate, explicitly authorized copy.
- Before each Alembic command, verify the effective `DATABASE_URL`. Upgrade,
  downgrade, and autogenerate are not read-only diagnostics; migrating a
  copy does not authorize the same operation on the operational database.
- Before accepting requests, the backend lifespan compares the exact set
  of deployed Alembic heads with the database's current heads. On file-based
  SQLite, the check uses `mode=ro`; a missing, unversioned, outdated, newer,
  or differently branched database stops startup before the health check.
  The check does not create databases and never automatically runs
  `upgrade`, `stamp`, or `create_all`.
- A verified online backup, also copied to another drive, is required before
  migration or downgrade. No procedure may suggest deleting the database
  as a normal remedy for locks, tests, or an outdated schema.
- `lint` may format files (Black/isort) as well as check them; it must not be
  described as a purely read-only command.
- A modern backup is valid only if its source file is the one configured
  for the application and the database/manifest pair passes hash, integrity,
  foreign key, and revision checks. The SQLite Online Backup API is the
  only supported internal path; a raw copy of the live file is not supported.
- Restore remains disabled by default and fails closed if any of
  `RESTORE_ENABLED`, enabled backups, or the expected revision is missing.
  When enabled, it uses the crash-safe protocol in ADR 006: quiescence,
  system lock, pre/post verification, pre-restore backup, staging and swap
  on the same filesystem, a durable journal, and fault injection. It must
  never be bypassed by manually replacing the operational file or sidecars.
- The backend must remain on loopback. Host/Origin and the volatile
  capability protect HTTP mutations, but are not authentication and do not
  make network exposure safe.

### 12.7 Dependency Reproducibility

- Reference runtimes: Python 3.14.6, Node.js 26.4.0, and npm 11.17.0.
- On Windows AMD64/Python 3.14, setup installs `backend/pylock.toml` with
  hashes; a deliberate upgrade regenerates the lock and validated versions
  and requires the full suite, including relevant migration/backup tests.
- The frontend always uses `npm ci`; `package.json` and `package-lock.json`
  change together.
- The POSIX path must not be described as equally reproducible until hashed
  locks and CI exist for every supported combination (`R-13`).

## 15. Glossary

| Term | Definition |
|------|------------|
| **FIFO** | First In, First Out: internal convention for matching lots chronologically; does not certify tax treatment |
| **TWR** | Time-Weighted Return: return with the effect of cash flows removed |
| **MWR / IRR** | Money-Weighted Return / Internal Rate of Return: return that accounts for the timing and amount of flows |
| **Total Return** | Return that includes both price changes and income (dividends, coupons) |
| **YoC** | Yield on Cost: income yield calculated on the historical cost basis |
| **Current Yield** | Income yield calculated on the current market price |
| **Unrealized Gain/Loss** | Capital gain/loss on securities still held in the portfolio |
| **Realized Gain/Loss** | Capital gain/loss crystallized by completed sales |
| **P&L** | Profit & Loss: statement of profits and losses |
| **ISIN** | International Securities Identification Number: unique identification code for a security |
| **Ex-Date** | Dividend/coupon ex-date: holders of the security on this date are entitled to payment |
| **WHT** | Withholding Tax: tax withheld at source (for example, on foreign dividends) |
| **ADR** | Architecture Decision Record: a document recording an architectural choice and its rationale |
